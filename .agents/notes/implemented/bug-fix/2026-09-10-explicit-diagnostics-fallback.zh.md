# Agent Note：明确的诊断模式兜底

状态：已实现

[English](2026-09-10-explicit-diagnostics-fallback.md) | 中文

## 问题

当前 Profile 启动失败后，安装包自带的恢复 Profile 仍可能正常就绪。桌面端此前会把这个最小 Profile 当成普通 Harness 工作区展示。由于它刻意不读取用户设置和第三方插件，用户可能再次看到首次引导、发现设置项和插件消失，却看不到已经进入恢复状态的明确说明。

## 决策

恢复 Profile 继续作为安装包自带的内部进程，为受限恢复操作提供支撑，但绝不再作为 Harness 主界面打开。它就绪后，桌面端停留在明确的“诊断模式”页面，并把当前 Profile 的原始启动错误保留为主要证据。该页面提供插件卸载、插件快照、配置目录安全切换、诊断导出和打开本机日志目录。

用户选择重新尝试时，客户端先停止诊断进程，再正常启动当前 Profile。诊断进程本身若也失败，只作为有界的次要失败记录。诊断进程就绪不能证明当前 Profile 或恢复后的插件快照健康。

本决策取代[Profile 诊断与安全启动](../feature/2026-08-25-profile-diagnostic-safe-mode.zh.md)中面向用户展示安全模式工作区的做法。内部的 `DSH_PROFILE_SAFE_MODE` 启动原语和诊断设置文件仍然保留，因为它们负责为恢复页面提供隔离进程。

## 考虑过的替代方案

**继续展示最小 Profile，只增加提示横幅。** 功能残缺的工作区仍会把缺失设置和插件展示成普通产品状态，依赖插件的诊断能力也仍然不可用。独立恢复页可以明确划定能力边界。

**不启动任何诊断进程，直接停止。** 静态日志导出和配置目录切换仍可使用，但依赖安装方运行时的受保护恢复流程会失去有界执行环境。

## 结果

用户不会再进入一个看似正常、实则功能残缺的工作区。正常启动前即可明确查看原因和日志，失败 Profile 的第三方插件也不会被加载。只有当前 Profile 真正恢复正常后，完整产品功能才会开放；这是有意的失败关闭，而不是退化运行模式。
