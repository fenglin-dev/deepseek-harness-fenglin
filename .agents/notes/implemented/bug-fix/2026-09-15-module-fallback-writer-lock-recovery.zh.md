# Agent Note：共享依赖写锁恢复

状态：已实施

[English](2026-09-15-module-fallback-writer-lock-recovery.md) | 中文

## 问题

`healProfilesModuleFallback` 等待 `profiles/node_modules.lock` 超时后，桌面端此前只会以 `profile.unknown` 进入诊断模式。页面不能区分仍在工作的写入进程和孤立锁，不能显示锁中记录的 PID，也没有边界明确的修复操作。重新安装应用无效，因为该锁属于被保留的用户数据目录。

## 决策

Profile 诊断分类器现在只把 `profiles/node_modules.lock` 的精确原子写入超时归类为 `profile.module-fallback-lock-busy`。桌面主进程只检查这一处固定锁，并且只向恢复页面返回状态和锁中记录的 PID。

只有操作系统确认该 PID 已死亡时，恢复按钮才会启用。清理前会重新读取这个普通且非符号链接的锁，确认其身份未变化，并再次检查 PID，随后以原子移动再删除的方式清理。PID 仍存活、无法确认存活状态、文件损坏、符号链接、文件已消失或验证期间被替换时，一律不删除。渲染层不能提交路径或 PID。

## 考虑过的替代方案

**启动时删除所有原子写入锁。** 这可能移除合法写入进程持有的锁，使应用读取正在发生变化的 Profile。

**允许渲染层提交锁路径或 PID。** 这会把单一恢复操作扩大为通用文件删除或进程检查能力。

**把无法访问的 PID 当作已死亡。** 权限错误不能证明进程已经退出，因此存活状态未知时仍禁止清理。

## 结果

诊断页面现在会指出真实故障、显示持锁进程，并在存活进程退出后自动更新状态。确认孤立的锁可以在不修改插件、会话、设置或凭据的情况下清理并重试正常启动。无法确定的情况仍保持阻塞，等待人工检查和导出诊断。
