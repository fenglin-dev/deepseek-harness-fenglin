# Agent Note: NAS 运行端选择

Status: implemented

[English](2026-09-17-nas-runtime-selection.md) | 中文

## 问题

仅在桌面端运行的 Harness 会把插件、模型设置、会话和工作区保存在一台电脑上。通过网络文件系统共享其数据目录，会暴露仅适用于本地的锁和包布局假设；直接把普通 Web Profile 开放到局域网，则缺少设备身份与撤销边界。

## 决策

Desktop 将每个 NAS 部署视为独立运行端，而不是本地 Harness 进程使用的远程数据目录。Docker Compose 部署拥有 `/config` 与 `/workspaces`，通过一个专用 HTTPS 根域名提供服务，并运行同一个社区 Web Profile。选择 NAS 后，Desktop 会重启并连接该来源，不会启动本地 Harness；NAS 不可用时也不会静默回退。

NAS 生成一次性八位配对码，并且只持久化随机设备 Bearer grant 的 hash。Desktop 使用操作系统安全存储封装 grant，必要时固定经过核对的自签名证书指纹，并且只向精确匹配的已选来源发送 grant。设备查看与撤销使用固定路由。局域网发现只提供不受信任的地址建议，仍必须核对证书并完成配对。

远程 renderer 只获得缩减后的 Electron bridge。它可以管理已保存的运行端选择，并使用明确保留的设备本地展示功能；不会获得插件安装、进程控制、诊断、命令行注册、任意文件系统、环境变量或 Shell 能力。插件、模型、会话和工作区归服务端所有；窗口等设备展示偏好归客户端所有。

## 曾考虑的替代方案

**把桌面数据目录放在 SMB 或 NFS 上。** 不予采纳，因为 Profile 锁、pnpm 链接、原生依赖、原子替换和进程所有权都属于本地文件系统契约。网络存储会让同一个目录表面上可共享，却无法保证并发与跨平台包状态安全。

**使用共享密码开放普通 Web Profile。** 不予采纳，因为共享 Secret 无法标识或撤销单台设备，而且会把边界扩大为笼统的浏览器信任，而不是绑定来源的桌面 grant。

**运行本地 Harness 并同步部分文件。** 不予采纳，因为会话、插件事务、凭据与工作区之间的冲突需要一套新的分布式一致性协议。由一个 NAS 运行端持有数据，所有桌面端才能看到相同的已提交状态。

**信任 mDNS 发现。** 不予采纳，因为组播广播未经认证。发现功能只作为可选便利入口，绝不会绕过 HTTPS 身份核对或配对。

## 后果

不同电脑可以通过同一运行端使用相同的会话、插件、模型与工作区，并可逐台撤销设备。NAS 断线会明确展示，用户必须重试或显式切回本机。运维者需要提供域名解析、HTTPS、可写持久化挂载、备份与升级。自签名部署会增加一次指纹核对步骤；mDNS 需要 Linux host 网络，否则需手动输入地址。

首版面向 Linux x64 与 arm64 Docker 主机及专用根域名。它不支持 URL 子路径、任意本地能力转发、容器自动更新、静默数据迁移，也不支持本地进程同时直接使用 NAS 的存储目录。
