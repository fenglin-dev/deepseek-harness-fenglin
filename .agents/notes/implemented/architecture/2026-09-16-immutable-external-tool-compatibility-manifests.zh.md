# Agent Note: 不可变外部工具兼容清单

Status: implemented

[English](2026-09-16-immutable-external-tool-compatibility-manifests.md) | 中文

## 问题

外部工具解析器此前只比较桌面核心版本，并移除预发布后缀。因此，`0.1.5-rc.1` 与 `0.1.5-rc.2.1` 等版本会接受同一份滚动签名清单，但与其中一个构建共同审核的 Provider 坐标可能依赖另一个构建尚未具备的 Host 行为。精确 npm 软件包坐标可以避免跟随 dist-tag，却不能让已经发布的桌面构建继续绑定该构建审核过的坐标。

## 决策

每个桌面版本拥有一份 schema v2 兼容清单；其中的 `desktopVersion` 是包含预发布和构建部分的完整应用版本，公开文件名也包含该完整版本。Desktop main 只请求这个文件名，并且只有在签名文档的完整解析内容与安装包内置清单相等时才会采用。网络、签名、有效期、身份、精确版本或内容任一不匹配时，客户端会在有效时使用经过验证的缓存，否则使用内置坐标。

仓库把每份 schema v2 源清单保存在以桌面版本命名的目录中。仅允许 master 的 Pages 工作流会把这些文档展开为唯一公开文件名，在发布前逐个与已经存在的公开文件按字节比较，发现内容不同就失败，而不是替换。一次 GitHub OIDC 证明覆盖所有保留清单。部署产物包含完整保留集合，因此新增桌面版本不会移除旧版本 URL。

Provider、原生运行时、完整性值或审核基线任一变化都需要新的桌面应用版本和新清单。发布门禁要求当前应用版本存在匹配的源目录，并在打包前继续验证精确 registry 坐标及平台软件包。

## 考虑过的替代方案

**每条核心版本线使用一份滚动清单。** 否决，因为预发布后缀经常代表 Host 构建存在实质差异，而旧客户端无法证明后续审核覆盖过自己的代码。

**使用签名 semver 范围。** 否决，因为范围仍允许后续发布重新解释已经发布的客户端。完整版本与不可变内容让所选坐标成为应用构建本身的属性。

**只使用安装包内置清单。** 否决，因为签名版本 URL 与缓存保留了可以独立验证的发布记录，也能在不授予远程坐标变更能力的情况下延续现有离线恢复路径。

## 后果

旧桌面构建永远不会采用为后续 RC、稳定版或重新构建引入的 Provider 或运行时坐标。支持更新的外部工具运行时需要发布另一个桌面版本。使用旧滚动端点编译的客户端在端点不可用时会安全回退到自身内置坐标，但只有重新构建后才能获得 schema v2 的不可变性。

## 验证

桌面测试会拒绝完整版本相同但坐标变化的文档，拒绝同一核心版本下的其他预发布版本，验证带版本 URL 与证明主体，保留经过验证的缓存回退，并固定并发查询共享。发布测试要求带版本的 v2 目录、通配多主体证明、签名前按字节比较、仅 Pages 权限以及不修改 GitHub Release。registry 门禁要求当前桌面版本的源清单存在，并验证其中的 Provider、运行时、可选平台包与 SHA-512。
