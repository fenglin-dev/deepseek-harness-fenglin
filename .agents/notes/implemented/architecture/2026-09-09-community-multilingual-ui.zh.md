# Agent Note：社区版多语言 UI 架构

Status: implemented

[English](2026-09-09-community-multilingual-ui.md) | 中文

## 问题

上游 Client 有意只内置中文和英文，外部语言包可逐个 namespace 增加语言。社区桌面端还包含在 Client locale 服务可用前就会显示的 Electron 文案；PR #19 提供了正确的俄语功能字典，却没有统一负责语言可用性、启动语言选择与跨平台回退的 owner。若继续在菜单、preload 页面和各功能中复制 locale 条件，后续翻译将难以审计，也容易误翻译路径、包名和用户数据。

## 决策

Open DSH Desktop 按固定顺序发布统一社区语言目录：`zh`、`en`、`ja`、`ko`、`es`、`fr`、`de`、`pt-BR` 与 `ru`。`ui-desktop-shell` 通过一个可逆 Cordis effect 负责注册额外七种语言定义及其按语言拆分的静态字典包。各功能包仍是中文与英文的事实来源；社区字典包镜像当前 Client 的完整 namespace 范围，不修改上游功能包。未来缺少的 key 沿该语言声明的英文 fallback 查找，而不是在展示代码中混入局部字面量条件。

Electron 自有页面使用 `desktop-locale.ts` 统一处理 BCP 47 与下划线标签、字典选择和具名插值。解析器绝不翻译路径、URL、插件身份、命令或外部错误值。首次配置目录选择器也从同一目录动态生成语言选项，并为每个可选语言提供完整文案；页眉让可变宽度控件参与正常布局，空间不足时自动换行。选择器外壳始终限制在视口内，底栏保持可见，翻译后增高的内容则在左右内容区内部滚动。Harness 就绪前，原生菜单和恢复页使用原子写入的 `userData/desktop-locale.json`，读取上一次生效的 Profile 语言；若没有有效缓存，再回退到操作系统语言，最后回退到英文。Client 报告当前 Profile 的生效语言后，该值成为权威并刷新缓存。

macOS 应用菜单、Windows/Linux 标题栏菜单和托盘右键菜单都从同一个当前语言解析文案；切换语言后，两类原生菜单会立即刷新。社区字典以当前的 `sidebarDocumentPreview` 及各渲染器 namespace 替换已经废弃的 `sidebarTextpreview`，并镜像官方右侧栏现有的停靠控件。因此无需修改上游侧边栏功能包，也能完整翻译文件、Markdown、PDF、HTML、代码和图片预览界面。

俄语中与 `@ragnoryok1/dsh-client-locale-ru@0.1.1` 重叠的值逐字复现该包在提交 `03907139127361cad255371442b37b264059ff23` 中的字典；社区字典包另行补充 Desktop 独有 namespace 和较新的 key。日语重叠部分以提交 `c354fd6456543c9d9b3b92fd97d8aa5559dd5525` 中的 `@fang2hou/dsh-locale-ja@0.2.0` 为准。两份来源均采用 MIT 许可证，其声明随本包发布。韩语、西班牙语、法语、德语和巴西葡萄牙语覆盖相同的当前 key 范围。每种语言存放在独立静态模块中，因此可以单独审阅或替换，而无需改写其他语言。

## 验证

locale 测试固定稳定 id、地区与下划线匹配、英文回退、Unicode 与 Windows 路径、未知占位符、损坏缓存恢复及原子缓存内容。Client 生命周期测试固定语言目录注册、七种社区语言的翻译查找和完整释放。内置语言测试要求 namespace 与 key 集合一致、占位符集合一致，并禁止翻译传输标记泄漏。源码比对会验证全部俄语重叠项与固定外部字典一致；另一项源码界面比对会把每种社区语言的右侧栏和文档预览 namespace 固定到当前上游的精确 key 集合，避免上游新增控件后静默显示英文。原生应用菜单和托盘测试覆盖全部公开语言及英文回退。首次配置目录选择器还会检查每个可选语言都有完整非空文案，并用可换行页眉布局承载较长的语言名称和开发按钮文案。

## Alternatives considered

**把俄语作为与中文、英文并列的特殊内置语言。** 否决，因为之后每增加一种语言都要修改核心运行时，并会把社区翻译变成上游 locale 约定。

**把社区字典分别复制进每个上游功能包。** 否决，因为这会把社区专属维护分散到整个上游合并面。桌面端拥有的字典包保留 namespace 边界，同时把派生翻译集中在一个包中。

**在运行时翻译缺少的字符串。** 否决，因为 UI 文案必须保持确定性、支持离线、可审阅，并且不能依赖网络或第三方翻译服务。

**Harness 启动前只使用操作系统语言。** 否决，因为 Profile 明确选择其他语言时，恢复页和原生菜单会在启动期间切换语言；最小化桌面缓存无需写入 Profile 即可保持这些界面一致。

## 后果

- 新增可选语言与翻译覆盖只需改一次社区目录；中文和英文文案仍留在决定其语义的功能侧。
- 翻译者可以单独编辑一种语言模块，无需修改 LocaleRuntime 或上游功能包。
- 每种内置语言覆盖相同的当前 namespace 和 key 范围；未来新增的源文案在字典更新前回退到英文。
- Profile 就绪后，其语言同时控制 Client 与原生桌面 chrome；启动和恢复阶段通过桌面缓存保持一致。
- 缓存只保存展示状态，不含路径或凭据，也绝不覆盖已经就绪的 Profile。
- 复数规则与双向布局仍由语言包负责；本次改造不虚构基于字符串的复数约定。
